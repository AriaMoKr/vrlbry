# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

vrlbry is a WebXR virtual library. A Node.js server scans a directory (default: the cwd) for `*.zim` files (openZIM archives; Project Gutenberg ones from gutenberg2zim and Wikisource ones from mwoffliner get special handling), exposes their books over a small JSON API, and serves a Three.js client. The client shelves the books in a 3D library room and lets you pull a book out, open it and read it page by page. It works in a VR headset, on a desktop (mouse + keyboard) or on a phone (touch).

**`SPEC.md` is the binding contract between modules** (section numbers like §3.5 are referenced from code comments). Keep it in sync when you change an interface, JSON shape or the block format. `TODO.md` lists open work.

## Commands

```bash

npm start                        # = node server/index.js (serves ZIMs in the cwd over HTTP on :8080)
node server/index.js --dir <path> --port 8080 --host 0.0.0.0
npm run start:https              # HTTP :8080 + HTTPS :8443 in one process (self-signed cert in .cert/; needed for a headset over LAN)
node server/index.js --no-watch  # do not rescan the folder while running
node server/index.js --kiwix-serve http://<host>:8095/   # full-text search through kiwix-serve (Kiwix's server, serving the same ZIMs)
npm test                         # = node --test "test/*.test.js" (a bare directory arg does not work); runs tsc too (test/types.test.js)
npm run types                    # = tsc -p tsconfig.json: the type check alone
npm run build:pages              # static site for GitHub Pages into dist/ (tools/build-pages.mjs)
npm run build:pages -- --zims <dir>   # … with the ZIMs in <dir> pre-rendered as static files
npm run build:pages -- --indexes <dir>  # … with the indexes of <dir>'s Wikipedia/Wikisource ZIMs under indexes/ (for visitors who open those files)
node tools/build-indexes.mjs --zims <dir>   # prebuilt indexes of tools/indexes.txt's current editions into .indexes/ (from local copies; --web: from Kiwix's mirror)

node --test test/zim.test.js     # one test file
node --test --test-name-pattern="redirect" test/zim.test.js   # tests matching a name

A test checks the built site for root-relative URLs and unresolved imports.
- **Branches and sites.** `main` (AriaMoKr/vrlbry, remote `gh`) publishes https://ariamokr.github.io/vrlbry/ with `.github/workflows/pages.yml`. Two other branches, each in its own repo as its default and only branch, published their own flavour (both repos private since 2026-10-10, their Pages sites gone): `vrlbry-standalone` (AriaMoKr/vrlbry-standalone, remote `gh-standalone`, `pages-standalone.yml`: reading ZIM files in the browser) and `vrlbry-cloud` (AriaMoKr/vrlbry-cloud, remote `gh-cloud`, `pages-cloud.yml`: milestone 3, ZIMs read straight from Kiwix's mirror, Kiwix's library, prebuilt indexes). Both were merged back into `main` on 2026-10-10 (branch `merge-cloud`, merge commit `cfc92f0`) and are parked: new work goes on `main` directly; they may be used later for trying new features or particular needs. When merging between them, keep each target's own workflow and leave the others out (`688d4ce` removed `pages.yml` on the standalone branch). Each site is self-contained: none loads files or indexes from another, so any one can be removed without the others noticing. The main site's workflow: the demo set (`tools/demo-set.txt`) part pre-rendered (`--zims`), part shipped as the ZIM files themselves (`--zim-files`: a line's second word `file`; opened in the browser with each visit), each ZIM in its smaller form, ~460 MB (ZIM files are shipped exactly as Kiwix publishes them, never split or repacked: the same size and hash); its own prebuilt indexes (its Actions cache and its release "indexes"; the missing ones built from Kiwix's mirror by hand with `indexes.yml`, the quickest first, apart from the deploys so a push is published at once, starting a deploy when it has new ones), shipped while the site stays within 950 MB (`build-indexes.mjs --ship --budget-mb`; Pages publishes at most 1 GB); the proxy when its repository variable `ZIM_PROXY` is set. The three sites are flavours of one app on one origin (`ariamokr.github.io`) and share its localStorage and IndexedDB on purpose, so stored formats must stay compatible across them (settings kept whole with unknown fields, no database version bumps, versioned names for derived data: TODO, milestone 3 step 6, "Shared storage"). Only Kiwix's own mirror, `mirror.download.kiwix.org`, allows a browser's range reads (CORS); the other six send no CORS headers (TODO, milestone 3).
- **GitHub Pages** (`.github/workflows/pages.yml`, on push to `main`): `tools/build-pages.mjs` copies `public/` (minus the dev pages, which need the server), the three/IWER modules the client imports (followed through their imports), and static API answers (`api/libraries` with `"static": true`, `api/version`). With `--zims` it runs the server in-process and saves every answer the client can ask for as a file under `api/library/<id>/` (`books.json`, `books/<id>/index.json`, `books/<id>/chunks/<n>.json`, Wikipedia `titles.json`) plus the images under `zim/` (§4). File names go through `fileName` (`public/js/util/file-names.js`, shared with `api.js`): a name Windows cannot store (Wikipedia images with `"`) is saved percent-escaped and its URL names the escaped file (`staticFile` / `staticUrl`); names over 200 bytes are shortened with a hash (`storableName`). A Wikipedia's articles are pre-rendered in the order the ZIM stores them (`ArchiveLibrary.articlesInStorageOrder`), so each cluster is decompressed once: in title order Medicine mini took 30 min, now 2 min. The build fetches its answers uncompressed (`accept-encoding: identity`). In static mode `api.js` asks for those names and searches Wikipedia titles itself; the client hides Rescan, and a first visit opens the demo set. Pages lets browsers reuse every file for 10 minutes and a reload only revalidates the page, so the build tags every module URL with a version (`?v=<hash>` per group: app, three, IWER; `versionUrls`), including the import map, where each `three/addons/…` module the app imports gets an exact entry, and `api.js` fetches `api/libraries` and `api/version` with `cache: 'no-cache'`. New module URLs must be static imports or `new URL('./x.js', import.meta.url)` for the build to tag them (a test checks every one). The workflow pre-renders the ZIMs listed in `tools/demo-set.txt` and ships those marked `file` as ZIM files (both cached in `.demo/`).
- **Types, a file at a time** (`tsconfig.json`): tsc checks the page's modules from their JSDoc, as they are served; nothing is built or emitted. `checkJs` is off: a file joins with `// @ts-check` as its first line once `npm run types` finds nothing in it, and the others are read for their types only (31 files have joined; the subclass in `ui/text-view.js` first). `npm test` runs it (`test/types.test.js`), so the Pages workflow does too. The page names common by its served URL (`../vendor/common/<module>.js`), which is no folder here: `rootDirs` lays `types/served` over `public`, where `types/served/vendor/common/<module>.d.ts` re-exports the package's own types (`export * from 'common/<module>.js'`); a checked file that imports a vendor module without one fails (TS2307). In JS a JSDoc `{object}` is `any`, and tsc does not see fields set with `Object.assign` (Interaction's `controls` and `settings`): `ui/text-view.js` names what it reads of them in its `Interaction` typedef. `@types/three` is at three's version.
- There is no build step, bundler or linter. The client is plain ES modules in `public/`. An import map resolves `three` → `/vendor/three/build/three.module.js` and `three/addons/` → `/vendor/three/examples/jsm/`. The server maps `/vendor/three/*` to `node_modules/three/*` and `/vendor/iwer/*` to `node_modules/iwer/build/*`.
- Conventional ports: **HTTP 8080, HTTPS 8443** (`--port`, `--https-port`).
- WebXR needs a secure context. `http://localhost` works. A headset on the LAN needs `https://<ip>:8443`, or `adb reverse tcp:8080 tcp:8080`.
- The embedded browser pane rejects the self-signed certificate, so use the HTTP port (8080) for browser testing.
- Dev pages: `/reader-test.html` is a 2D reader built on the page renderer, and `/dev/world-test.html` shows the room with an orbit camera.
- **Performance on the headset:** `/?perf` turns on the recorder (`public/js/perf.js`, exposed as `__vrlbry.perf`). `node tools/quest-perf.mjs run --open` (or `dump` / `status`) collects it over adb with the VrApi log, memory and battery figures, and writes `perf/quest-*.json` (gitignored). `run` first reloads a page that was opened before the last change (`__vrlbry.version` vs `GET /api/version`); otherwise you would measure old code. `--desktop` measures on the PC instead, in a Chrome window of its own (common's `tools/chrome.mjs` `launchChrome`, whose new profile causes no failed Windows logon; never start Chrome by hand on a new profile for it). During `run` the headset acts as if worn (an adb broadcast overrides its proximity sensor: `PROXIMITY` in the tool; given back at the end, or `--no-prox` to leave it alone), so it needs no tape over the sensor. `run` also traces garbage collection (CDP `Tracing` of V8's GC events) and reports per scenario how many dropped frames had a GC pause in them. Instrument new heavy work with `perf.event(name, { t, ms, … })`, which does nothing unless recording. `quest-perf.mjs handover` checks the VR hand-over (SPEC §5.7): it enters VR, takes the way out (`--to <url>`, else the page itself) and times the next page's grant and session (`--runs`, `--delay`).
- **Scripted testing:**
  - Append `?xr=emulate` to the app URL to install Meta's IWER WebXR emulator (a virtual Quest 3). It is installed with `forceInstall`, because Chromium exposes a native `navigator.xr` even without a headset.
  - The app exposes `window.__vrlbry` (renderer, scene, camera, rig, world, controls, interaction, overlay, xrDevice, settings, together, `enterVR()`, `tick(dt, n)`).

  - In XR the XRSession drives frames. For tests in a hidden pane, replace `window.requestAnimationFrame` with a `setTimeout` version and restart the loop with `renderer.setAnimationLoop(() => __vrlbry.tick())`.

## Architecture: data flow end to end

```
*.zim ─► ZimArchive (core/zim) ─► ArchiveLibrary (core/library.js), Library (server/library.js) ─► HTTP API (server/http.js)
          (folder watched;            │ catalog: Gutenberg JSON index | Wikisource works index
           generation counter)        │          (core/wikisource.js, cached in .cache/) | generic HTML entries
                                       └ content: htmlToBlocks → chunkBlocks (core/content) + LRU cache
client: api.js ─► rooms.js (what to shelve) ─► World/Bookshelves ─► interaction.js state machine ─► Book3D
                └► BookReader (paginates blocks onto a 1024×1448 canvas) ─► Book3D page textures
```

### Server

- **`public/js/core/`** is the code the server and a browser share (step 2 on this branch: reading ZIMs in the browser). It never imports `node:*` or bare specifiers (a module worker has no import map); what differs goes through `core/platform.js`, which `server/platform-node.js` fills in on Node (zlib, crypto, files, htmlparser2, Buffers: so the server keeps Buffer's speed and its callers still get Buffers). Core code uses only `Uint8Array` features plus `platform.*` (`utf8`, `indexOf`, `alloc`, `copy`, …) and `core/util/bytes.js` (`u32`, `compareBytes`, …), never Buffer methods. Node code that uses core modules directly (tests) imports `server/platform-node.js` first.
- **`public/js/core/zim/reader.js` (`ZimArchive`)**: reads ZIM files with positional reads only, from a byte source: `ZimArchive.open(path)` (Node: `platform.openFile`), a `Blob`/`File` (`core/zim/blob-source.js`), or any `{ name, size, read(position, length), close() }`.
  - Binary search over the URL pointer list compares **bytes** of (namespace char + UTF-8 URL), not JS strings. UTF-16 order differs for astral characters.
  - Every read under 64 KB (dirents, URL pointers, cluster heads, small blobs) comes from a cache of aligned 64 KB blocks (`_readBlocks`, `blockCacheBytes`, 8 MB; the local library gives each file 16 MB). On a `File` in a browser a read costs about the same however small (on a Quest 3 ~65 ms alone, ~11 ms each when 8 or more run at once, a 4 MB read 87 ms; `perf/quest-reads-*.json`), so what counts is the number of reads: a lookup is one read per binary-search step (opening a 4.5 GB Gutenberg ZIM made 3,200 such reads over 1.7 MB of directory). Scans (`entries()`) read in batches and bypass it. The local library also sets `wholeClusterBytes` (4 MB): an uncompressed cluster that small is read whole into the cluster cache once a second blob of it is wanted (the first is read on its own: a book whose pictures lie one per cluster would otherwise read a cluster per picture), since a book's pictures usually share a few clusters; never for a size alone (`getBlobSize`). With `wholeCompressedBytes` (also 4 MB) a cluster that an entry's MIME type says is compressed is read in one read, head and all, not two. The server leaves all three at their defaults (its reads are cheap). Opening reads the directory's last 64 entries: metadata, `W/mainPage` and `X/…` lie there in every libzim file, so their lookups cost no binary search (`_tail`); the namespace scheme comes from the version (6.1+: new), as in libzim. Read many entries with `getEntriesByIndex` (neighbours with one read), not `getEntryByIndex` in a loop.
  - **Remote ZIMs (milestone 3):** `ZimArchive.open(url)` reads over HTTP range requests (`core/zim/http-source.js`: only a `Range` header, as the Kiwix mirror's CORS allows; each answer's size and Last-Modified checked against the first; a request made while others run asks for `cache: 'no-store'`, since a browser serializes range requests on a URL it has cached; the probe always does, as it decides the edition, and a cached answer that is whole (Chrome's `If-Range` after the file changed: every Pages deploy re-uploads the site's ZIMs), short or of another edition is asked again past the cache). Over the network a round trip costs 0.3–0.8 s and bytes cost time too, so URLs want small blocks (`blockBytes` 8 KB, measured best), no whole uncompressed clusters, `wholeCompressedBytes` 4 MB and `ArchiveLibrary.open`'s `checkImages: false` (a sized image is not looked up) and `bookLookups: 500` (a longer Gutenberg list's books are made from the list, their files looked up when first opened: `gutenberg_mul_all`'s 76,000 lookups took hours over the network). Every speed-up layer (caches, prebuilt indexes, a proxy, the catalogue) must stay optional: a URL or a file opens without any of them (TODO, milestone 3). The edge proxy (`tools/zim-proxy/`, step 7: a Cloudflare Worker reading the mirror nearest the visitor, with CORS) is the source's `via`: read first, dropped for the file's own address on its first failure; the library, its `url` and the block cache's keys stay Kiwix's mirror's. The page uses it only when the built page names it (`build-pages.mjs --zim-proxy`, the workflow's `ZIM_PROXY` variable) or `?zimproxy=` does. Windows reserves ports 8754-8953 here (`netsh interface ipv4 show excludedportrange protocol=tcp`), so wrangler's 8787 cannot be listened on. The measurements behind these choices are in the TODO (milestone 3, step 2).
  - **Uncompressed clusters are not read whole on the server.** Only the two offset-table entries and the blob byte range are read, because images and EPUBs can be tens of MB (the local library reads small ones whole: see `wholeClusterBytes` below).
  - Compressed clusters (zstd = 5, xz = 4 via the pure-JS `core/zim/xz.js`, zlib = 2) are decompressed asynchronously (`platform.zstd` / `platform.inflate`) into a byte-budgeted `LRUCache` (`core/util/lru.js`). Concurrent requests for the same cluster share one in-flight decompression.
  - Both namespace layouts are supported. The new scheme puts all content in `C`; the old scheme uses `A`/`I`/`-`.
- **Gutenberg catalog**: book list comes from `C/full_by_popularity.js` = `var json_data = [[title, author, formatsFlags, bookId, lccShelf], …]`, in popularity order.
  - `formatsFlags` is a `[html, epub, pdf]` string such as `"110"`. Some books are EPUB-only (`"010"`) and are made readable by parsing their EPUB (`core/content/epub.js`).
  - A book's entry URL mirrors the ZIM's own JS exactly: `title.replace("/", "-").substring(0, 230) + "." + id`. Only the **first** `/` is replaced, and the substring is in UTF-16 units. The HTML lives at that path, the EPUB at that path plus `.epub`, and the cover at `C/covers/<id>_cover_image.jpg`.
  - Titles may contain MARC ` : $b ` subtitle markers, which are split into title and subtitle.
  - **Kiwix's newer files (papers2zim, from 2026-11; §2.2)** have no such script: `C/config.json` names the source (`source.slug: "gutenberg"`: kind `gutenberg`; another source stays generic), and the books are the entries of `C/books-pages/popularity/<n>.json` (`books.json` says how many pages; `title/` when there is none), nothing else in the file (`_papersCatalog`). A book's id is its Gutenberg number, which the entry gives only in its `coverPath` (`covers/<n>_cover_image.webp`), so ids match the older files'; `primaryCollection` is its `shelf` (`P`, `G`, `CDEF`: C to F together, named in `LCC_NAMES`); the spaced colon left of MARC's `$b` splits title and subtitle (`splitPapersTitle`). Its files are looked up by title and number (`papersBases`: the scraper strips the title first), else from its own JSON's `formats` (`C/books/<slug>.json`; `_papersFiles`, also through `_resolveBook` for a long list). Pictures and covers are WebP. The page begins with `<div id="html-reader-controls">` (three icons), dropped by the converter. A file whose `M/Scraper` says papers2zim is not searched for `full_by_popularity.js`.
  - A ZIM with neither falls back to "generic" mode: its HTML articles become the books, capped.
- **Wikisource catalog (`core/wikisource.js`, §2.4/§3.8)**: books are multi-part works (a top-level page with subpages; 17,693 in the English ZIM).
  - The works index needs a full pass over the archive (~110 s for 8.6 GB), so `ArchiveLibrary` builds it in the background on first open and caches it as `.cache/wikisource-<uuid>.v<N>.json`. Indexes go through a store (`readText`, `writeText`, `readBytes`, `appendBytes`, …, by name): core's `ArchiveLibrary.open` takes `store`, and server/library.js's `ArchiveLibrary` turns `cacheDir` into one (`fileStore`, `server/cache-store.js`); with no store (a browser, for now) a built index lives in memory only (`_built`). Meanwhile `books()` is empty and `info().indexing` reports progress; on completion `onChange` bumps `Library.generation`. Bump its version (`core/index-versions.js`, which the page's Kiwix library also names indexes by) when the index format or build-time extraction changes.
  - Index builds (Wikisource and Wikipedia) go through the folder's `IndexQueue` (`core/util/index-queue.js`, `Library.indexQueue`): archives over 1 GB one at a time, smallest first (`indexing.stage` is `'queued'` while waiting); smaller ones at once. Builds share the main thread and libuv's four threads, so running them together only slowed each one down (8 Wikipedias at once: 52 min, Simple English 20 min instead of 1). A rescan holds the queue until every new archive is open.
  - mwoffliner strips the header template, so pages carry no author: authors come from `Author:` pages linking to works. Genre and year come from the categories embedded in each page (`"wgCategories"` in RLCONF), mapped at load time by `GENRES`, so genre rules can change without re-indexing.
  - Reading a work assembles the main page plus its subpages depth-first in link order (a non-root page may only pull in its own descendants), capped at 1200 parts / 36 MB.
- **Wikipedia catalog (`core/wikipedia.js`, §2.5)**: a room of volumes of 1,000 articles in the app's title order (`titleKey` + `Intl.Collator`, shared with `util/books.js`).
  - The index reads no article text. It scans the directory, reads each page's HTML size (each cluster decompressed once, in cluster order, several at once, from the scan's cluster/blob via `archive.clusterBlobs`: re-reading each directory entry made the full English Wikipedia take ~7 hours), keeping its progress in a checkpoint (`.cache/wikipedia-*.part.*`) so a restart resumes the size pass, to estimate lengths and to drop, from each page's first 4 KB (`pageKind`), mwoffliner's section-redirect pages (tiny `<meta http-equiv="refresh">` HTML), pages of other Wikipedia namespaces (`"wgNamespaceNumber"` not 0: the full English Wikipedia has 2.2 M Category pages) and "page not found" placeholders, then sorts. URLs starting with `_` are mwoffliner's own pages, never articles. It is built in the background and cached as `.cache/wikipedia-<uuid>.v<N>.json`, compact since v5 (`indexText`: the order as variable-length deltas, each size as one byte within 4 %, base64 in JSON: the full English Wikipedia's 74 MB became 20 MB); a v4 one found in a store, a site or `build-indexes.mjs --out` is upgraded, not rebuilt (`parseIndexV4`, `upgradeIndex`). Bump its version (`WIKIPEDIA_INDEX_VERSION` in `core/index-versions.js`) when the format or what counts as an article changes: a stale index is otherwise trusted.
  - A volume's `content()` is metadata only (`lazy`). `ArchiveLibrary.chunk(bookId, n)` converts one article on demand, and the HTTP chunk route always goes through `chunk()`.
  - Client: volumes are `ordered` (never re-sorted), have uniform `BOOK.volume` dims and their own spine and cover art (`textures.js`). They keep that order in the all-libraries hall too.
  - Full-text search (optional, server only): with `--kiwix-serve <url>` the server asks Kiwix's own server for the libraries whose file it serves too (same UUID: `fulltext: true`), since the library does not read the ZIMs' Xapian indexes itself (`server/kiwix-serve.js`, routes `text` and `find`, §4). `ArchiveLibrary.placeOf(path)` turns a hit's page into a book and place (`resolveLink` uses it too); `findText` finds the block a hit is in (`core/content/find.js`: the query's words first, since Kiwix's snippet can point at a book's contents list). The overlay lists hits under "In the text" (`findInText` in `search.js`; an empty list waits for them as for the articles, `asksText`: SPEC §5.6) and `interaction.openText` opens the book there; a Wikisource page past where its work was cut (1,200 parts) is reported (`beyond`), not opened.
  - Reading the ZIMs' Xapian indexes ourselves (experimental, not used by the app yet; docs/SEARCH.md, option 4): `core/zim/xapian.js` (`XapianDb`: the Glass format worked out from the bytes, not from Xapian's GPL code; a full-text index holds Snowball-English stems, so a query needs the stemmer: `porter2` in the tools, `npm install --no-save porter2`), `tools/xapian-measure.mjs` (a file or an address, `--kiwix` to compare), `public/dev/xapian-test.html` (the browser, through the proxy). Over HTTP each 8 KB block is a request: read a search's blocks in batches (`prefetch`), never one after another.
  - Article search: `GET /api/libraries/:lib/articles?q=` binary-searches the sorted index by title prefix (`searchIndex`) and finds other names through the ZIM's redirects in the URL index (`searchRedirects`); the overlay lists the results after its book results, and `interaction.openArticle` opens the volume at that article. The contents panel of a volume gets a thumb index (`thumbIndex`).
  - The converter moves a `table.infobox` (its first image stays at the top, the rest goes under "Quick facts" after the lead) and drops sidebars and other MediaWiki chrome. Inline formulas and small icons are **image runs** (`["\uFFFC", bits, { src, w, h, va? }]`, §3.5), laid out inside the line of text; anything iterating runs must allow for that third element.
- **Library titles** (`libraryTitle`, §4): Kiwix's Gutenberg ZIMs of one LCC class all have the title "Project Gutenberg Library", so they are shown as "Gutenberg · <class> (<CODE>)" from their description and name, and the whole collections (`gutenberg_<lang>_all`) as "Gutenberg · every book (<LANG>)" or "… in every language"; Wikipedia minis and nopics of a topic get "(introductions)" / "(no pictures)" from the ZIM's Flavour. `zimTitle` keeps the ZIM's own.
- **Rescans**: `Library.rescan()` / `watch()` add, remove and reopen archives while running and bump `generation`. `GET /api/libraries` returns it and `POST /api/rescan` triggers a scan; clients poll every 10 s. They also poll `GET /api/version`: once the site's files change (a Pages deploy, edited client files) the page runs old code, so it stops applying catalogue changes and asks for a reload (a banner, the kiosk's reload button, a notice in VR; the banner and notice can be turned off: `settings.updateNotices`, back on in the help dialog). A page left open across a deploy otherwise took a new ZIM into the catalogue but not into the Demo set, whose list is in the old `rooms.js`.
- **Content model (§3.5)**: book HTML is converted on the server into compact JSON **blocks**, then grouped into **chunks** (~40k chars) delivered one at a time. This is because one book in the reference ZIM is 30 MB of HTML.
  - Block types: `t` = `h` / `p` / `li` / `tr` / `pre` / `img` / `hr`.
  - Text is stored as `Run = [text, styleBits]` tuples. Style bits: 1 italic, 2 bold, 4 mono, 8 sup, 16 sub, 32 smallcaps, 64 underline, 128 smaller, 256 larger.
  - `"\n"` inside a run is a hard line break. Optional fields are omitted when they hold their default value.
  - The library layer rewrites image `src` from archive paths to client URLs: `/zim/<lib>/<ns>/<url>`, with each path segment percent-encoded. It also fills in missing image width/height by sniffing the image header bytes.
  - The converter strips scraper-injected nav (`span.zim_*`), page markers (`.pagenum`) and MediaWiki/mwoffliner chrome (`MW_CHROME_CLASSES` / `MW_CHROME_IDS` in `content/html.js`).
  - **Links** are runs too: `[text, bits, link]`, the link object holding `at: [c, b]` (a place in the same book: references, sections, Gutenberg contents and footnotes, a Wikisource work's parts; tied to their blocks by `linkDocs` and placed by `chunkBlocks`), `href` (an archive path, resolved when followed: `ArchiveLibrary.resolveLink`, the `…/books/:id/link?to=` route, the worker's `link`) or `to: { book, c, b?, f? }` (resolved; the static build turns every `href` into one). Each visitor shares where in the library they are (`spaceOf`: place and room filters, which decide the layout) as `<DOOR_ID>.space.<memberId>` (written on the controller's `session` event and again on the session's `self`, and by `setSpace`), and the controller's `isHere(peer, avatar)` (the same space, the key kept on the avatar; must not allocate: it runs every frame) decides who is drawn and counted `here`; `nearby` is "elsewhere in the library". Its vendor modules are named by relative URL (`../vendor/layersharedsession/…`), not through the import map: `server/vendor.js` rewrites their bare imports (`trystero` → `trystero-nostr/index.mjs`, …) and the build resolves them among the vendor URLs (`vendorResolve`), since a vendor name need not be its package's folder.
- **`util/books.js`**: holds the sort comparators, `letterOf` and `bookDims`. Both the shelf layout and the A–Z jump / interaction code **must** use these shared helpers so they agree on order and book sizes. Shared constants (dimensions, page size, reading pose, `XR_FRAME_RATE`) are in `config.js`.
  - Sorting is cached, because libraries reach 60,000+ books (the Quest took 2 s per room switch before the caches). Each book's sort keys are computed once, and comparisons use one shared `Intl.Collator`, which gives the same order as `localeCompare`. `sortBooks` caches its result per input array and mode, and `shelfCollections` filters a room out of the library's sorted order. Never mutate a library's book array in place; replace it.

## Testing notes

- Tests use `node:test` + `node:assert/strict`. Tests that need the real ZIM (`gutenberg_en_lcc-pe_2026-03.zim` in the repo root, ~795 MB, not committed) `skip` when it is absent. The repo root holds other ZIMs too, so open the reference archive directly (`ArchiveLibrary.open`); never take the first library a folder scan finds.
- Synthetic ZIMs for unit tests are written by `test/helpers/zimwriter.js`. It supports both namespace layouts, all cluster compressions, extended clusters and redirects.
- `test/wikisource.test.js` builds a miniature mwoffliner-style archive (RLCONF categories, skin chrome, `Author:` pages). The real 8.6 GB Wikisource ZIM is not used by the test suite.
- `test/client-*.test.js` run the pure client modules (`util/books.js`, `reader/layout.js`, shelf packing, `rooms.js`) in Node. Layout tests use a fake text measurer, since Node has no canvas. Client `blockChars` must stay identical to the server's; a test checks this.
- `test/client-lod.test.js` runs `Bookshelves` itself in Node with a stub 2D canvas. It covers atlas LOD, the atlas worker (with a fake worker, plus a guard that the worker imports only relative modules), pointer rays and partial vertex uploads. Pass `atlasWorker: null` to paint on the main thread.
- Client modules that import vendor packages by relative URL (`hallway.js`, `nav.js`, `world/door.js`, `xr/gamepad.js`, `ui/text-view.js`: `../vendor/common/…`; `together.js`: `../vendor/layersharedsession/…`) are tested through `test/helpers/vendor.js`: import it, then the module dynamically (`await import(…)`); it maps `public/vendor/<name>/` onto node_modules as the server does (`server/vendor.js`). `test/client-together.test.js` runs the session over a stand-in for the layer's session module (`joinSession`). `test/client-panel.test.js` runs common's `Panel` itself, as interaction.js uses it. `test/client-keep-focus.test.js` runs `ui/keep-focus.js` over a small DOM of its own (`test/helpers/focus-dom.js`: nodes moved and removed, the focus falling to `<body>`, `:focus-visible`, each focus move counted).
- `test/types.test.js` runs tsc (`tsconfig.json`) and fails with its messages: a file with `// @ts-check` that no longer type-checks, or a missing `types/served` re-export.
- `test/perf.test.js` covers the `?perf` recorder and the parsers in `tools/quest-perf.mjs` (adb output on Windows is CRLF).
- The xz test vectors in `test/fixtures/xz/` (`<name>.xz` + expected `<name>.sha256`) are regenerated with `python test/fixtures/xz/generate.py`, which uses Python's `lzma` module.
